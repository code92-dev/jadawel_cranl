# PORT MAP — Builder responsive columns + burger menu (upstream Baserow 2.3.3 → Jadawel 2.2.2 fork)

Target capability

- (a) `ColumnElement` gains `layout_type`, `column_weights`, and per-device `column_stacking`.
- (b) `MenuElement` gains a per-device `expanded`/`compact` variant with burger rendering.

All `baserow.*` imports become `jadawel.*`; `@baserow/...` becomes `@jadawel/...`; `baserow-icon-*`/`baserow-icon-settings` become `jadawel-icon-*` where the fork already renamed them. Premium/enterprise code is out of scope and is not involved here.

Bottom line up front: **both features are independent of the 2.3 graph migration, `action_scopes.py` and `elements/trash_types.py`.** See §4.

## Risk notes

1. **Migration numbering and the 0068 trap (highest risk).** The fork's `builder` head is `0068_jadawel_rename_local_jadawel_models`, and `integrations/0030_jadawel_rename_local_jadawel_pg_objects` depends on it (`0030:87`). Upstream's `0069` depends on `0068_alter_page_unique_together`, which must **not** be ported (see §3). Port the two field migrations as `0069` and `0070`, both depending directly on the fork's `0068`. If someone instead copies upstream filenames verbatim, Django will either raise `NodeNotFoundError` or, worse, apply `0068_alter_page_unique_together` and drop `("builder", "name")` uniqueness.
2. **`0072`'s dependency on the graph migration.** Copying `0072` verbatim leaves a dependency on a migration that will never exist in the fork, and the whole `builder` app then fails to build its migration graph. Re-point it to the local variant migration. Evidence that nothing else is needed: upstream `0071:66-141` contains the only `RunPython`, and neither `0069` nor `0072` reads `graph` or any `compat_*` column.
3. **`MenuElement.vue` requires `MenuItem.vue`, a new file.** The upstream 2.3.3 component no longer renders menu items inline — it delegates to `MenuItem` (`MenuElement.vue:53, 73, 86`). Fork's copy is the 2.2.2 inline version (fork `MenuElement.vue:1-96` markup, `203-280` methods). Porting the compact branch *without* `MenuItem.vue` silently loses active-item highlighting, sub-link `Context` menus and button click dispatch. The faithful port is `MenuElement.vue` + new `MenuItem.vue` in one commit. If inline rendering must be preserved instead, the minimal alternative is to keep fork's markup and wrap it in the compact container, but then `useInlineSubLinks` (`MenuItem.vue:164-172`) has no home and sub-links inside the burger panel will still open a `Context` popup. Decide once; do not ship a half-split.
4. **RTL / logical-property drift in the scss.** The fork has deliberately converted builder scss to logical properties (`inline-size`, `block-size`, `margin-inline-start`, `inset-inline`) as part of the RTL work (`docs/RTL_REVIEW.md`), while upstream 2.3.3's `column_element.scss` and `menu_element.scss` use physical `width`/`height`/`left`/`max-width`. Overwriting those two files upstream-style will regress RTL (the compact panel in particular is anchored `left: 0` with `border-radius: 0 6px 6px 0` upstream `menu_element.scss:135-145`). Merge rule-by-rule and convert to logical equivalents; verify the compact panel in `ar` with `dir="rtl"`.
5. **Public pages never set the device type.** Fork `PageContent.vue:87-89` (and 2.2.2, identical) only sets `dimensions.targetElement`; upstream adds the `closestDeviceType(window.innerWidth)` dispatch in `mounted` (`PageContent.vue:59-63`). Because `page` store defaults `deviceTypeSelected: 'desktop'` (fork `store/page.js:35`), `useCompactMenu` (`MenuElement.vue:139-141`) and `shouldStackColumns` (`ColumnElement.vue:109-115`) would evaluate against `'desktop'` on first paint of every public page, so the burger and smartphone stacking never appear until the user resizes. This hunk is a functional prerequisite, not cosmetic.
6. **Existing menus change appearance after the migration.** `0069` back-fills `variant` with `{desktop: expanded, tablet: compact, smartphone: compact}`, so every pre-existing menu becomes a burger on tablet and smartphone immediately after deploy. That is the upstream intent, but it is a user-visible behaviour change on live applications and should be called out in the changelog.
7. **`db_default` + callable default.** Note the deliberate asymmetry in upstream `models.py:432-437` and `0072:48-63`: `default=get_default_column_stacking` (callable, evaluated per instance) but `db_default=get_default_column_stacking()` (a single dict literal evaluated once at import). Replicate exactly; a shared dict would be a mutation hazard, and swapping the callable for a literal would make all instances share one object.
8. **`column_stacking` / `variant` dicts can arrive partial.** Additive merges matter: the form merges the default over whatever the API returns (`ColumnElementForm.vue:213-221` `this.values.column_stacking = {smartphone, tablet, desktop, ...(this.values.column_stacking || {})}`), and the components guard with optional chaining (`MenuElement.vue:141`, `ColumnElement.vue:112-127`). Preserve both guards; a menu element created before migration and never re-saved will have no `variant` key at all on the read path if the API default is not applied.
9. **Do not port the `validate_place_in_container` → `validate_position_as_child` rename, nor `get_places`, nor the removal of `apply_order_by_children`.** The fork's `elements/registries.py:140` calls `parent_element.get_type().validate_place_in_container(...)` and fork tests (`elements/test_column_element_type.py:23-80`) assert `get_new_place_in_container`, `get_places_in_container_removed`, `apply_order_by_children`, and `validate_place_in_container`. Upstream renamed/removed all of these as part of the graph work; porting that rename without the graph subsystem breaks element creation outright.
10. **Two ways to satisfy the dual-property styles serializer — pick one and be consistent.** The fork's `DynamicConfigBlockSerializer` already supports the nested-list form (`api/theme/serializers.py:34-62`), so the only required change is which kwargs are used at the `MenuElementType` call site. If the upstream keyword names are copied, the signature rename in `api/theme/serializers.py:18-19` and the 10 other call sites in `elements/element_types.py` must land in the same change or every other element type's styles field silently breaks (the constructor raises `ValueError("Missing property_name parameter")`).
11. **Serializer contract change ripples into export/import tests.** `serializer_field_names` growing on `ColumnElementType` changes the serialized nested-element config everywhere, including `test_builder_application_type.py` (upstream `:564-571, 993-1000`) and `elements/test_repeat_element_type.py` (`:79-86`). Those expected dicts must gain `column_weights`, `column_stacking`, `layout_type` in the same change, or CI fails on unrelated-looking assertions.
12. **`layout_type` default must stay the string `'auto'`.** The frontend compares against bare strings (`ColumnElement.vue:131-160` uses `'custom'`, `'1:2'`, …) and `ColumnElementForm.vue:239` emits `'custom'` for >3 columns; DRF `ChoiceField(default=ColumnElement.LAYOUT_TYPES.AUTO)` yields the enum member, which compares equal to the string on the wire. Keep `required=False` and the same help_text so the OpenAPI schema matches upstream (`element_types.py:176-181`).
13. **`ColumnElementType` has no `serializer_field_overrides` in the fork.** Adding one must spread `**super().serializer_field_overrides` first (`element_types.py:175` upstream) or the `ContainerElementTypeMixin`/`ElementType` overrides are lost. This is a genuinely new property in the fork, not an edit of an existing block.
14. **`pageElementSections.js` is a decoy.** It appears in the upstream diff of `PagePreview.vue`/`PageContent.vue`, but it belongs to the 2.3 page-sections/fixed-header rework (upstream `PAGE_ELEMENT_BEHAVIOURS`, migration `0075`, `getPageSection`). Porting `PagePreview.vue` wholesale from upstream would drag in the sections mixin, the fixed-header/footer behaviour and the `page__fixed-stack` scss. Port only the four `setPagePreviewLocked`/`isPreviewLocked` hunks listed in §2.
15. **Django version.** Both trees' migrations were generated on Django 5.2.x and the fork pins `django==5.2.17` (`backend/pyproject.toml:18`), so `db_default` on `CharField`/`JSONField` is fully supported; no compatibility shim is needed for the two new migrations.
