## Risk notes

1. **Concurrent edits were observed mid-investigation.** File mtimes in `backend/src/jadawel/core/` moved from "5h ago" to "1-2m ago" during this run, and `backend/src/jadawel/core/duration.py` did not exist at my first glob yet existed at my second. All backend "PRESENT" claims above are point-in-time verifications against the current on-disk content; re-check `git status` before assigning work, and do not let a second agent re-create `duration.py`, `service_file.py`, or the `runtime_formula_types.py` additions.
2. **`settings.FORMULA_RANGE_MAX_ITEMS` is a live crash, not a nicety.** The fork's `RuntimeRange.execute` (`runtime_formula_types.py:784-788`) reads `settings.FORMULA_RANGE_MAX_ITEMS`. Any `range()` formula evaluated today raises `AttributeError`. Fix first, independently of everything else.
3. **The frontend base-class contract change is a silent-divergence trap.** `validateTypeOfArgs` in `modules/core/runtimeFormulaTypes.js` currently returns `null`/`arg` (2.2.2). 2.3.3 returns an array of `[index, arg]` tuples, and `validateArgs` consumes `results[0]`. If the new function classes are pasted in without changing the base class, `RuntimeToDuration.validateTypeOfArgs` (which returns `[[1, args[1]]]`) will be misread: `if (invalidArg)` is truthy for a non-empty array, but `InvalidFormulaArgumentType` receives the whole array as `arg`. Port the base class and `validateArgs` in the same commit as the new classes.
4. **`_parseArgsForValidation` must change or `to_duration` mis-validates.** Fork `formulaValidationVisitor.js` still does per-index parsing of every argument during validation, so `RuntimeToDuration.parseArgs`'s deliberate deferral of arg 0 (when a format is given) never runs at validation time. Symptom: valid `to_duration('1:30', 'h:mm')` formulas may fail validation, or invalid ones pass, depending on the raw string. Fix together with item 3.
5. **Duration semantics must not fork in two.** The fork currently has exactly one duration implementation in JS (`modules/database/utils/duration.js`, the 2.2.2 non-token engine). Introducing `modules/core/utils/duration.js` creates two implementations unless `modules/database/utils/duration.js` is immediately reduced to the re-export shim. The database-field path (`formatDurationValue` with `DURATION_FORMATS.get(format).toString`, `parseDurationValue` with `DURATION_REGEXPS`) and the new formula path (`formatValueWithDurationFormat` token engine, `DURATION_TOKEN_FORMATS`) produce subtly different output for the same input; the upstream shim guarantees both routes share the token engine. The fork already applied the equivalent backend change (`fields/utils/duration.py:409-428` delegates to `format_value_with_duration_format`), so the JS side must follow, otherwise FE/BE formatting diverges on fractions. Regression surface: `test/unit/database/utils/duration.spec.js` (14 format cases) and `test/unit/core/formula/runtimeFormulaTypes.spec.js`.
6. **Rounding differs by construction between the two engines, and the upstream token engine is the arbiter.** Token engine rounds half-up on the absolute value _before_ decomposing fields so carries propagate (`duration.py:232-246` / `duration.js:175-190`); the old `DURATION_FORMATS[].round` rounds the raw seconds first. Any FE test asserting 2.2.2 rounding for `h:mm`/`d h` may need expectation updates — do not "fix" one side to match the other; make the shim authoritative and let both sides call it.
7. **`DURATION_TOKEN_FORMATS` is duplicated across the language boundary and must stay in sync.** Backend `fields/utils/duration.py:201-212` and forecast JS `modules/core/utils/duration.js:527-537` carry the same 10-entry map with backslash-escaped unit letters (`r"d\d h\h"`). Comments on both sides say "Keep in sync with duration.py::…". Drifting one side changes CSV/JSON export versus grid display for the same row.
8. **Locale parity has a zero-missing baseline.** `scripts/locale-parity-baseline.json` sets `maximumMissingKeys` to 0 for `locales`, so every English key added here must land in `ar.json` in the same change or the parity check fails. Note also that `formulaParserErrors` is currently missing in **both** languages while `errors.js` already calls `i18n.t(...)` on those paths — that is a pre-existing latent bug this port should close, not a new one it introduces.
9. **Editor extension swap is the highest-regression-risk piece and is separable.** Replacing `FunctionDetectionExtension` + `GroupDetectionExtension` + `OperatorDetectionExtension` with `InputDetectionExtension`, and adding `FunctionDowngradeExtension` + `ParenMatchHighlightExtension` + `helpers.js`, touches the advanced-mode editor used by every formula input. The existing fork specs (`ZWSManagementExtension.spec.js`, `fromTipTapVisitor.spec.js`, `toTipTapVisitor.spec.js`, `FormulaInputField.spec.js`) exercise this surface. The runtime-function port (items 1-7) is independent of it and can land first; the extension swap can be deferred without blocking `to_duration`/`range`/`number_format` from working.
10. **`duration_format` vs `format_duration` is a naming landmine with an upstream red herring.** The runtime function is `duration_format` (backend `:941`, frontend `:3186`). `format_duration` is also a real symbol but a **field-type method** (`DurationFieldType.format_duration`, `contrib/database/fields/field_types.py:2212`) and a **helper function** (`fields/utils/duration.py:409`), and it appears in `enterprise/backend/website_export.csv:7215,7272` as documentation prose listing "`format_duration()`" among user-facing formula functions. Registering `format_duration` as a runtime function would be wrong and would collide with the field-type method name in the docs; register `duration_format`.
11. **`ServiceFile`/`ensure_file` arrived as dead code.** `backend/src/jadawel/core/formula/service_file.py` exists and `validator.py:23-39` defines `ensure_file`, but nothing in the fork calls them (the upstream consumer is `contrib/integrations/core/service_types.py:2035-2038`, which has no fork equivalent). They import cleanly (`UserFile`, storage, `advocate`), so this is harmless, but it is unexercised surface — do not assume it is battle-tested, and do not add `ensure_file` to public exports without a consumer.
12. **`RuntimeRange` limits differ between the two implementations.** Backend raises `BaserowFormulaSyntaxError` when `len(range(...)) > max_items` (`runtime_formula_types.py:785-788`); frontend returns `null` when `count > maxItems` (`runtimeFormulaTypes.js:2743-2747`) and also returns `null` for `step === 0` where the backend raises. Pasting the frontend class without also keeping the max-items config wired means an unbounded client-side allocation; keep the `$config.public.formulaRangeMaxItems` guard.
13. **Python 3.14 bytecode cache present** (`__pycache__/*.cpython-314.pyc`) confirms the backend edits were compiled/imported, not just written. Absence of `backend/tests/jadawel/core/test_duration.py` means the new `core/duration.py` has **no test coverage in the fork yet** despite being exercised by field formatting — worth adding, since the token engine is now on the critical path for CSV/JSON export (`DurationFieldType.format_duration` -> `format_duration_value` -> `format_value_with_duration_format`).
